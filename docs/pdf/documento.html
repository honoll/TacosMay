1. Introducción y dominio del problema

TacosMay nace de las taquerías de mi familia. La idea de negocio es vender sus guisos ya cocidos, empacados al vacío en porciones y enviados a cualquier parte de México, para que el cliente solo abra la bolsa, caliente y coma. El producto es perecedero: cada lote tiene pocas porciones y una vida útil limitada, así que el inventario es chico, cambia rápido y no se puede vender dos veces.

La aplicación es la tienda en línea de ese negocio. Un cliente se registra, consulta el catálogo de guisos y los más vendidos, arma un carrito y confirma su pedido. Un administrador da de alta, edita y da de baja guisos y su existencia. El dominio impone cuatro necesidades:

  1. Lectura dominante. El catálogo se lee muchísimo más de lo que se escribe.
  2. Datos temporales. El carrito debe desaparecer solo si el cliente lo abandona, para no acumular basura.
  3. Concurrencia sobre el stock. La existencia debe descontarse sin vender de más cuando dos clientes compran la última porción al mismo tiempo.
  4. Ranking en vivo. El negocio quiere ver en todo momento qué guisos se venden más.

Las cuatro son accesos por clave conocida, con expiración y con contadores. Por eso el proyecto usa el modelo Clave-Valor con Redis, alojado en Redis Cloud.

Alcance. El proyecto cubre catálogo, cuentas, carrito y pedidos. Quedan fuera pagos, cotización de envío y lotes con fecha de caducidad. El menú y los precios cargados por el script de datos iniciales son de ejemplo y están marcados como tales; los reales se definirán con el negocio.

2. Justificación del paradigma

2.1 Qué pide el dominio y cómo responde cada modelo

NecesidadEn Redis (este diseño)En un SGBD relacionalVeredicto

2.2 Lo que se pierde y cómo lo compensa el diseño

Se pierdeConsecuenciaCómo se resuelve
JoinsNo se puede pedir «pedidos con sus guisos» en una consulta.El pedido guarda sus items como JSON, con nombre y precio copiados al momento de la compra. Además de evitar el join es lo correcto: un pedido no debe cambiar si después cambia el precio.
Consultas no previstasSolo se puede preguntar lo que se diseñó. «Ventas de marzo por guiso» no tiene clave que la responda.Cada consulta que la aplicación sí hace tiene su estructura (ranking, pedidos por usuario, índice de guisos). Un reporte nuevo exige una estructura nueva o exportar los datos.
Integridad referencialRedis no impide borrar un guiso que está en un carrito.La cuida la aplicación: al borrar un guiso se quita también del índice y del ranking en la misma transacción; el carrito omite guisos que ya no existen y el checkout los rechaza con 409.
Esquema y tiposUn Hash acepta cualquier campo y todo se guarda como texto.Un solo validador (utils.validar) y una sola función que convierte el Hash a objeto con números.
Unicidad declaradaNo existe UNIQUE.El correo es la clave (tm:user:{email}): no puede haber dos.
RollbackRedis no revierte una transacción si un comando falla dentro del EXEC.Se valida todo antes de encolar; dentro del MULTI solo van comandos que no fallan por tipo.
DurabilidadEn el plan gratuito los datos viven solo en memoria.Se acepta para el proyecto y se declara (sección 4.4); el script de datos iniciales repuebla la base.

2.3 Conclusión

Un SGBD relacional puede hacer todo lo que hace esta aplicación, y a este volumen lo haría con holgura; el argumento no es de capacidad, es de ajuste. Las cuatro operaciones centrales del dominio (leer por clave, expirar solo, contar y ordenar por ventas, descontar con control de concurrencia) son primitivas del motor en Redis, mientras que en SQL dos de ellas (la expiración y el ranking siempre ordenado) hay que construirlas encima. El costo es real y se asume de forma explícita: se renuncia a los joins, a las consultas no previstas y a que el motor cuide la integridad. El diseño lo compensa desnormalizando los pedidos, creando una estructura por cada consulta necesaria y concentrando las validaciones en una sola capa del backend. Si el negocio creciera hacia reportes, facturación o pagos, lo razonable sería añadir una base relacional para esos datos y dejar a Redis el carrito, el ranking y el catálogo.

3. Arquitectura de la solución

  • Cliente. Página estática servida por el mismo Express (express.static), por lo que llama a /api/… con rutas relativas y no necesita CORS. Todas las peticiones pasan por una sola función api() que agrega el token y convierte los errores en excepciones.
  • Backend. Sigue la estructura por capas del backend desarrollado en clase (rutas → middleware → controladores → modelos). Los controladores validan y responden; solo los modelos hablan con Redis.
  • SDK de conexión. Driver oficial redis (node-redis 6). Hay un único cliente compartido, creado al arrancar con REDIS_URL, con manejador del evento error. El servidor no acepta peticiones hasta que la conexión está lista y se niega a arrancar si falta la variable, para no conectarse por omisión a localhost.
  • Credenciales. REDIS_URL, JWT_SECRET y las credenciales del administrador viven en .env, excluido del repositorio; .env.example documenta cada variable.
  • Base de datos. Redis Cloud, plan gratuito: 30 MB de memoria y 30 conexiones simultáneas (Redis, s.f.-a).

4. Diseño del modelo NoSQL

4.1 Convención de nombres de claves

Formato tm:{entidad}:{identificador}, con dos puntos como separador. El prefijo tm: aísla la aplicación dentro de la base, de modo que el script de datos iniciales puede limpiar solo lo suyo. Los plurales (tm:guisos, tm:pedidos:{userId}) son colecciones o índices; los singulares son una entidad. Ninguna clave se escribe a mano en el código: todas salen de backend/config/keys.js.

ClaveTipoContenidoTTL
tm:guiso:{id}Hashnombre, descripcion, precio_centavos, porciones, stock—
tm:guisosSetIds de todos los guisos: índice para listar sin recorrer la base—
tm:guisos:vendidosSorted SetMiembro = id del guiso, puntaje = unidades vendidas—
tm:seq:{entidad}StringContador para generar ids (guiso, user, pedido)—
tm:user:{email}Hashid, nombre, email, password (hash bcrypt), rol—
tm:carrito:{userId}HashCampo = id del guiso, valor = cantidad30 min, renovado en cada cambio
tm:pedido:{id}Hashid, userId, total_centavos, creado, items (JSON)—
tm:pedidos:{userId}ListIds de los pedidos del usuario, el más nuevo primero—

4.2 Por qué cada estructura

  • Hash para guisos, usuarios y pedidos. Son objetos con campos. El Hash permite leer el objeto completo con una operación y modificar un solo campo sin reescribir el resto; el stock se descuenta con HINCRBY, que es atómico.
  • Set como índice de guisos. Listar el catálogo cuesta lo que mide el catálogo. La alternativa, KEYS tm:guiso:*, recorre todas las claves de la base y bloquea el servidor mientras lo hace.
  • Sorted Set para el ranking. Mantiene los miembros ordenados por puntaje; sumar una venta y leer el top 5 no requieren recalcular nada.
  • Hash con TTL para el carrito. Cada campo es un guiso y su valor la cantidad, así que cambiar una cantidad es una sola escritura. El TTL vive en la clave completa.
  • List para el historial. LPUSH deja el pedido más nuevo al frente y el orden cronológico sale gratis.
  • JSON dentro del pedido. Los items se leen siempre completos y nunca se modifican: guardarlos como una cadena JSON evita una clave por renglón y congela nombre y precio de la compra.
  • El correo como clave del usuario. El inicio de sesión busca por correo, así que esa es la clave; de paso garantiza que no haya dos cuentas con el mismo correo.

4.3 Estrategia de expiración (TTL)

El carrito es el único dato temporal. Cada vez que el cliente agrega, cambia o quita un guiso, el backend escribe el campo y vuelve a fijar la expiración en 1800 segundos, de modo que el plazo corre desde la última actividad y no desde la creación. Modificar un campo de un Hash no altera el TTL de la clave, por eso se renueva de forma explícita. La API devuelve expira_en_segundos, leído con TTL, y la tienda lo muestra como cuenta regresiva. Al vencer, Redis elimina la clave por sí mismo: de forma perezosa cuando alguien intenta leerla y de forma activa con un muestreo periódico de claves con expiración (Redis, s.f.-b).

Catálogo, usuarios, pedidos y ranking no expiran: son datos del negocio.

4.4 Políticas de persistencia

RDB (instantáneas)AOF (bitácora de escrituras)
Qué guardaUna copia compacta de todos los datos cada cierto tiempo.Cada comando de escritura, en orden.
A favorUn solo archivo, bueno para respaldos; reinicio rápido.Más durable; la bitácora solo crece al final.
Cuánto se puede perderLo escrito desde la última instantánea.Con appendfsync everysec, hasta un segundo.

Fuente: Redis (s.f.-c).

Política de este proyecto. La base corre en el plan gratuito de Redis Cloud, que no ofrece persistencia en disco (Redis, s.f.-d): los datos viven en memoria. Sobreviven a reiniciar la aplicación, que es lo que muestra la demostración, pero no hay garantía si el nodo de Redis se reinicia. Se asume para el proyecto y se cubre con un script de datos iniciales reproducible (npm run seed). Para producción la política sería AOF con sincronización cada segundo, disponible en los planes de pago: los pedidos y el stock representan dinero y perder como máximo un segundo es aceptable.

4.5 Límites conocidos del diseño

  • El carrito no aparta stock. La existencia se revisa al agregar y se descuenta al confirmar; entre un momento y otro, otro cliente puede llevarse la última porción y el checkout responde 409. Un apartado real sería otra clave con TTL que reserve unidades.
  • El checkout no reintenta. Si la transacción se cancela por un cambio concurrente, responde 409 y el cliente vuelve a confirmar.
  • Escribir el carrito y fijar su TTL son dos comandos, no una transacción. Si la conexión se cortara justo entre ambos, un carrito nuevo quedaría sin expiración. Se corrige agrupándolos en un MULTI.
  • Conexión sin cifrar. La URL de la demostración usa redis://. En producción debe usarse TLS (rediss://).

5. Catálogo de consultas

Cada consulta aparece como el comando de Redis y como el método del SDK tal como está en el repositorio. client es el cliente único de backend/config/redis.js y keys el constructor de claves.

5.1 Conexión

// backend/config/redis.js
const { createClient } = require('redis')
const client = createClient({ url: process.env.REDIS_URL })
client.on('error', (error) => console.error('Error de Redis:', error.message))
await client.connect()

5.2 Crear (C): alta de un guiso

INCR  tm:seq:guiso                         → 7
MULTI
HSET  tm:guiso:7 nombre "…" descripcion "…" precio_centavos 18000 porciones 4 stock 20
SADD  tm:guisos 7
EXEC
// backend/models/guisosModel.js
const id = String(await client.incr(keys.seq('guiso')))
await client.multi()
    .hSet(keys.guiso(id), datos)
    .sAdd(keys.guisos, id)
    .exec()

El Hash y su entrada en el índice se escriben en la misma transacción para que nunca exista uno sin el otro.

5.3 Leer (R): un guiso y el catálogo completo

HGETALL  tm:guiso:7
SMEMBERS tm:guisos                         → ids; después un HGETALL por id
const findById = async (id) => desdeHash(id, await client.hGetAll(keys.guiso(id)))
const findMany = async (ids) => (await Promise.all(ids.map(findById))).filter(Boolean)

const findAll = async () => {
    const ids = await client.sMembers(keys.guisos)
    return findMany(ids.sort((a, b) => a - b))
}

Los HGETALL se lanzan juntos con Promise.all en lugar de esperar uno por uno; node-redis agrupa en un mismo envío los comandos emitidos en el mismo ciclo, lo que reduce los viajes de red a la nube. findMany se reutiliza en el catálogo, el carrito, el ranking y el checkout.

5.4 Actualizar (U): edición parcial de un guiso

EXISTS tm:guiso:7
HSET   tm:guiso:7 precio_centavos 12000    → solo cambia ese campo
if (!(await client.exists(keys.guiso(id)))) return null
if (Object.keys(datos).length) await client.hSet(keys.guiso(id), datos)

5.5 Eliminar (D): baja de un guiso con limpieza de índices

MULTI
DEL  tm:guiso:7
SREM tm:guisos 7
ZREM tm:guisos:vendidos 7
EXEC
const [borrados] = await client.multi()
    .del(keys.guiso(id))
    .sRem(keys.guisos, id)
    .zRem(keys.vendidos, id)
    .exec()
return borrados > 0

Es la integridad referencial hecha a mano: el guiso desaparece del catálogo, del índice y del ranking a la vez.

INCR    tm:seq:user
HSET    tm:user:ana@correo.com id 2 nombre "Ana" email "…" password "$2b$10$…" rol cliente
HGETALL tm:user:ana@correo.com
await client.hSet(keys.user(user.email), user)        // password = bcrypt.hash(password, 10)
const user = await client.hGetAll(keys.user(normalizar(email)))

5.7 Especializada: carrito con expiración (TTL)

HSET    tm:carrito:2 7 2                   → 2 porciones del guiso 7
EXPIRE  tm:carrito:2 1800                  → renueva los 30 minutos
HGETALL tm:carrito:2
TTL     tm:carrito:2                       → segundos restantes; -2 si ya no existe
HDEL    tm:carrito:2 7                     → quitar un guiso
DEL     tm:carrito:2                       → vaciar
// backend/models/carritoModel.js
const TTL_SEGUNDOS = 30 * 60

const setItem = async (userId, guisoId, cantidad) => {
    const key = keys.carrito(userId)
    if (cantidad === 0) await client.hDel(key, guisoId)
    else await client.hSet(key, guisoId, cantidad)
    await client.expire(key, TTL_SEGUNDOS)
}

const [hash, ttl] = await Promise.all([client.hGetAll(key), client.ttl(key)])

5.8 Especializada: ranking de más vendidos (Sorted Set)

ZINCRBY tm:guisos:vendidos 2 7             → suma 2 ventas al guiso 7
ZRANGE  tm:guisos:vendidos 0 4 REV WITHSCORES   → top 5, de mayor a menor
const top = await client.zRangeWithScores(keys.vendidos, 0, 4, { REV: true })

5.9 Especializada: checkout con bloqueo optimista (WATCH + MULTI/EXEC)

WATCH   tm:carrito:2
HGETALL tm:carrito:2
WATCH   tm:guiso:7
HGETALL tm:guiso:7                         → se valida existencia y stock en la aplicación
INCR    tm:seq:pedido                      → 1
MULTI
HINCRBY tm:guiso:7 stock -2
ZINCRBY tm:guisos:vendidos 2 7
HSET    tm:pedido:1 id 1 userId 2 total_centavos 24000 creado "2026-11-17T…" items "[…]"
LPUSH   tm:pedidos:2 1
DEL     tm:carrito:2
EXEC                                       → nulo si alguna clave vigilada cambió
// backend/models/pedidosModel.js (resumen)
const conexion = client.duplicate()          // WATCH es por conexión
await conexion.connect()
try {
    await conexion.watch(keys.carrito(userId))
    const carrito = await client.hGetAll(keys.carrito(userId))
    await conexion.watch(Object.keys(carrito).map(keys.guiso))
    const pedido = armarPedido(carrito, await Guiso.findMany(Object.keys(carrito)))
    const id = String(await client.incr(keys.seq('pedido')))

    const multi = conexion.multi()
    for (const { guisoId, cantidad } of pedido.items) {
        multi.hIncrBy(keys.guiso(guisoId), 'stock', -cantidad)
        multi.zIncrBy(keys.vendidos, cantidad, guisoId)
    }
    multi.hSet(keys.pedido(id), {
        id, userId,
        total_centavos: pedido.total_centavos,
        creado: pedido.creado,
        items: JSON.stringify(pedido.items)
    })
    multi.lPush(keys.pedidos(userId), id)
    multi.del(keys.carrito(userId))
    await multi.exec()
} catch (error) {
    if (error instanceof WatchError) {
        throw httpError(409, 'El stock cambió mientras comprabas, intenta de nuevo')
    }
    throw error
} finally {
    conexion.destroy()
}

Si otro cliente modifica el carrito o cualquiera de los guisos entre la lectura y el EXEC, Redis no aplica ningún comando y el driver lanza WatchError; la API responde 409. El WATCH se hace en una conexión propia porque el cliente compartido atiende a la vez otras peticiones, y una vigilancia en él se mezclaría con las de los demás (Redis, s.f.-f). Las transacciones de Redis ejecutan sus comandos en serie y aislados, pero no tienen rollback (Redis, s.f.-e); por eso toda la validación ocurre antes del MULTI, en la función pura armarPedido, que es la que cubre la prueba automatizada.

5.10 Historial de pedidos (List)

LRANGE  tm:pedidos:2 0 -1                  → ids, el más nuevo primero
HGETALL tm:pedido:1
const ids = await client.lRange(keys.pedidos(userId), 0, -1)
const hashes = await Promise.all(ids.map((id) => client.hGetAll(keys.pedido(id))))

5.11 Datos iniciales: limpieza por prefijo sin bloquear

SCAN 0 MATCH tm:* COUNT 100                → se repite con el cursor devuelto
DEL  clave1 clave2 …
// backend/seed.js
for await (const claves of client.scanIterator({ MATCH: keys.todas, COUNT: 100 })) {
    if (claves.length) borradas += await client.del(claves)
}

SCAN recorre la base por partes; a diferencia de KEYS, no detiene el servidor.
